## Inventory decisions
- Options and variants are separate (see `docs/stock-module-schema.md`, "Variant or option?"). A variant is what hangs on the rack: counted, with a SKU and barcode, built from axes (size, colour, fabric, other). An option is a choice a customer makes when ordering, such as dupatta style: not counted, no SKU, an optional price adjustment and an optional photo per value.
- With variants, quantity lives on each variant. The dress-level count is hidden in the UI.
- The dress-level count is kept underneath and is not changed by variant movements. If all variants are deleted, it reappears with its last value (Shopify's behaviour).
- **Rule:** once a dress has variants, the dress-level quantity input stays editable but shows the note: "Quantity entered here is replaced by the variant quantities." The value is saved as a dress-level movement, kept apart from variant stock, and hidden. Variant quantities are what count.
- **Track quantity** is one checkbox on the dress. When on, the Variants table shows a Quantity column.
- No default variant. A dress with no options has no variant row.
- No "sell when out of stock" in inventory. Selling a piece that hasn't reached the rack is an order.
- Made-to-order is not an inventory concept. It moves to the order side as a customisation flag. Removed from the Inventory panel.
- Only units on the rack enter inventory.
- **SKU is an input.** It can be autogenerated, or the user types their own. Whether it is generated, and in what format, is a setting: see `docs/settings.md` (Stock → SKUs).
  - Dress form: an optional SKU field. Variant row and variant page: the SKU becomes an editable input (read-only today).
  - A SKU can be empty, so wherever one is shown, handle blank.

## Make-to-order timeline
- Each make-to-order dress has a lead time, for example 2 to 4 weeks. Stored as a minimum and maximum, in weeks.
- The customer sees the lead time on the dress. It is not an inventory quantity.
- Not in the schema yet. Lead time fields would be added to `stock_dresses` when we build the order side.

## Variant page (one variant's own fields)
Opened by clicking a variant in the Variants list. Same layout idea as Shopify's variant page: a variant list on the left, the selected variant's sections on the right.

- **Header:** option values (e.g. size "M", fabric "Net"), status (active or archived).
- **Images:** the variant's own photos. Set one as primary.
- **Price:** price override (falls back to the dress price), compare-at price, cost.
- **Inventory:** tracked toggle, quantity on hand, SKU, barcode. No locations, no "sell when out of stock".
- **Shipping:** weight, packed size (L × W × H), for the courier.
- **Not on the variant page:** channels, catalogs, title, description, options. These stay at dress level.
- **Options:** kept as they are now. Choices with a price adjustment, no stock, no variant page.

**Schema:**
- `stock_dress_variants`: `compare_at_price`, `cost`, `track_quantity`, `weight_grams`, `length_cm`, `width_cm`, `height_cm`.
- `stock_dress_images`: `variant_id` (null = dress photo, set = that variant's photo). One primary photo per variant.
- Null on any variant field means the dress value is used.

## Resolved
- Dress with no variants: the dress holds the count. Dress with variants: each variant holds its own count, and the dress-level count is hidden and kept apart from variant stock.

## Build notes (design chat)
Built from the canvas boards. Where the boards and the data disagreed, the data won:
- **Options and variants are separate cards.** Options are order-time choices, each value with a photo slot and an optional price adjustment, all edited in place (`OptionRow`). Variants are built from axes. Each axis is a card where values are typed like option values (Enter adds the next, paste “S, M, L” to add several). Generate then makes the combinations: rows built from other axes are moved onto the new ones, keeping price, SKU and stock, and an unsaved row that can't move is dropped. Removing an axis offers Undo. Saved rows have an editable SKU, price and quantity (a changed quantity is posted as an adjustment). Removing a saved variant archives it. Two variants with the same values are flagged before saving.
- **Photos live in Cloudflare R2.** `uploaded_images` is the gallery: one row per file, with a SHA-256 `content_hash` that is unique, so the same picture is never stored twice whatever its name. The picker hashes a file first and, if the hash is already there, selects the existing image instead of uploading. Uploads and deletes go through the Worker in `workers/image-upload/`, which holds the R2 binding (the browser never has keys). Deleting from the gallery removes the R2 object too, and is refused while a dress photo or option value still uses it. `stock_dress_images.image_url` and `stock_dress_option_values.image_url` hold the public URL.
- **Set up storage:** create the bucket, then from `workers/image-upload/` run `wrangler login` and `wrangler deploy`, and put the Worker URL in `.env.local` as `PUBLIC_IMAGE_WORKER_URL`. The Worker has no login check yet (see the note in its code): add Supabase JWT verification before real data goes through it. `image_url` is still free text in the other tables; restrict it to https plus the R2 host.
- **Upload progress** is an indeterminate bar, not a percentage (fetch can't report upload progress).
- **Make to order is a switch** on the dress (`made_to_order`). Off, an empty rack reads as Sold out; on, the design stays orderable. The lead time fields under it are a disabled placeholder ("Saved with orders") until the columns exist.
- **Save bar, like Shopify's.** No Save or Cancel buttons in the header. The first change slides a bar in at the top ("Unsaved changes", Discard, Save) that stays until one is chosen; leaving the page meanwhile asks first (`UnsavedGuard`). Saving keeps you on the page; a new dress opens its edit page. Only the name is required: a new dress starts as a draft, and Active needs a price. Errors show under the header.
- **Quantity** is posted as a `received` movement on create and as an `adjustment` movement when edited (dress form and variant page). Nothing writes the column.
- **Not built:** Toast, bulk Export and Delete (the selection bar only archives; delete would orphan ledger rows), a barcode field on the dress form (it lives on the variant page), a separate PricingPanel, InventoryPanel and ShippingPanel (they are cards inside `StockDressFormFields`).
- **Currency** reads PKR everywhere, as the rest of the app does. The doc above says Rs.
